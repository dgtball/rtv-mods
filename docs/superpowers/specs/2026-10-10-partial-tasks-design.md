# Частичная сдача заданий торговцу (PartialTasks, 4.12.0)

Дата: 2026-10-10.
Статус: принято (brainstorming с пользователем, макет `docs/mockups/partial-tasks/index.html`, выбран вариант B).
Область: вкладка торговца `Interface` (Tools → значок торговца → Tasks/Input), задачи сдаваемых предметов.
Референс механики: мод «Partial Task Hand-In» (Ryujiro, исходники в `%TEMP%\opencode\partialtasks\ex`) —
берём идею, но **не** копируем инъекцию фантомных предметов: она не нужна при нашем подходе.

## Цель

Дать игроку вносить требуемые предметы задачи торговцу **частями**, не дожидаясь полного комплекта,
и завершить задачу, когда леджер фактически покрыт. Поверх ванильной механики `Input` добавляется
кнопка **Deposit** и инлайн-прогресс на ячейках требований (вариант B макета).

Три правки:

1. **Кнопка Deposit** в ряду кнопок карточки задачи (рядом с Input/Complete) — списывает выделенные
   в инвентаре предметы в счёт задачи, помечает их в леджере, обновляет прогресс.
2. **Инлайн-прогресс** прямо на ячейке требования: бейдж `внесено / нужно` и галочка/зелёная рамка
   при закрытии слота. Отдельной строки прогресса нет.
3. **Завершение по леджеру**: когда все слоты требования покрыты вкладами, Complete разрешается без
   наличия предметов в инвентаре; при сдаче ничего лишнего не списывается (вносы уже ушли).

## Термины и данные

- **Задача** (`TaskData`, `res://Scripts/TaskData.gd`) — `trader`, `name`, `difficulty`, `description`,
  `deliver: Array`, `receive: Array`. `deliver` — массив `ItemData`, количество кодируется повторами
  (`["Beer","Beer","Beer"]` = 3 шт). Часть задач без `deliver` — завершаются не сдачей предметов,
  они вне механики (Deposit не показываем).
- **Слот требования** — ребёнок `Task.inputGrid` (инстанцированный узел `Item`). У него `slotData`
  (`SlotData.itemData.file` — ключ сопоставления, `SlotData.itemData.name` — подпись, `SlotData.amount`)
  — источник «нужного» количества и стабильного индекса. Порядок слотов совпадает с порядком
  `TaskData.deliver` и не меняется между открытиями вкладки.
- **Стопка инвентаря** — узел `Item` в `Interface.inventoryGrid`: `selected: bool`, `slotData.amount`,
  методы `State("Selected"|"Static")`, `UpdateDetails()` (перерисовывает подпись количества), а также
  `slotData.itemData.file` для сопоставления.
- **Леджер** — запись вкладов игрока: `{ task_key: { "индекс_слота": внесено } }`.
- **task_key** — `TaskData.resource_path`, если непустой; иначе `name + "::" + trader` (фоллбэк).

## Ванильная механика (что выяснено)

- `Interface.InitializeTasks()` заново создаёт карточки на каждое открытие вкладки (`Task.tscn`
  инстанцируется в `taskList`, зовётся `newTask.Initialize`). Значит построение UI прогресса и кнопки
  Deposit выполняем на каждом открытии — как Notes.
- `Interface.StartInput(target)` вводит в режим ввода: `inputTarget = target`, `isInputting = true`,
  `inputTarget.Default()`/`ResetInput()` (снимает прежние выделения ячеек).
- `Interface.InputSelection()`: клик по стопке инвентаря → `hoverItem.State("Selected")` +
  `inputTarget.AddInputItem(slotData)`; повторный клик — снятие.
- `Interface.Complete(data)`: `trader.CompleteTask(data)` → `DestroyInputItems(data)` (удаляет из
  `inventoryGrid` **все** дети со `selected`) → `GetOutputItems()` (награды из `inputTarget.outputGrid`)
  → `ResetInput()`.
- `Task._on_complete_pressed()` завершает задачу через `Interface.Complete`; доступность кнопки
  Complete определяется `Task.CanComplete()` (слот «удовлетворён», когда для него набрано нужное
  количество; ваниль опирается на выделения ячеек `inputGrid`).
- `Trader.CompleteTask(taskData)` (Trader.gd) — только `tasksCompleted.append` + `SaveTrader`
  + `UpdateProgression`; предметы не списывает, заметку не чистит (заметку чистит существующий
  хук `trader-completetask-post` из 4.11.0).
- `Loader.NewGame` создаёт свежий `TraderSave` → вклады сбрасываются с новой игрой. `Loader.SaveTrader`
  и `SaveTaskNotes` делают `load("user://Traders.tres") as TraderSave` и пересохраняют **тот же объект**
  → метаданные переживают round-trip.
- Сигнатуры `Task.CanComplete()` / `Task._on_complete_pressed()` известны из декомпиляции референса;
  имена методов подтвердить в логе загрузчика при первом запуске (несоответствие — предупреждение
  «no such method», хук просто не сработает).

## Хранилище

Вклады живут в **метаданных ресурса `TraderSave`** (`user://Traders.tres`), ключ `vtk_deposits`:

```
vtk_deposits = { "<task_key>": { "0": 3, "2": 1 }, ... }
```

Сериализация метаданных ресурса в `.tres` **проверена эмпирически** (Godot headless, пробник
`tools/pckdump/metatest.gd`: `SAVE_ERR=0`, значения читаются обратно). Поэтому сабкласс `TraderSave`
не нужен — храним словарь как meta и пересохраняем ресурс через `ResourceSaver.save` после Deposit.

- Пишем сразу после успешного Deposit (как `Trader.SaveTrader`), не откладывая на выход из вкладки.
- Очистка записи задачи — в `trader-completetask-post` (та же точка, где чистится заметка).
- Индексы словаря — строки (ключи `Dictionary`), значения — int.

## Поток UX

1. Открытие вкладки торговца → карточки построены. Для задач с `deliver` над ячейками требований
  показан текущий прогресс из леджера (напр. `3 / 10`, «осталось 7»), в ряд кнопок добавлена Deposit
  (неактивна, пока нет ввода).
2. Игрок жмёт **Input** у нужной задачи → обычный ванильный режим ввода, кликает нужные стопки
  инвентаря (`InputSelection`). Deposit становится активной, если выделены подходящие предметы.
3. **Deposit** — из выделенных стопок вычитается не больше «остатка» по соответствующим слотам,
   лишнее остаётся в инвентаре; вклады пишутся в леджер и в `user://Traders.tres`; прогресс ячеек и
   доступность Complete пересчитываются.
4. Когда леджер покрывает все слоты — Complete разрешается (даже при пустом инвентаре). Сдача идёт
   ванильным `Interface.Complete`: награды выдаются, леджер задачи очищается, заметка удаляется.
5. Непокрытые задачи ведут себя как в ваниле (сдача комплектом из инвентаря). Смешанный случай
   (часть внесена, часть сдаётся предметами) поддерживается: закрытые слоты помечаются
   удовлетворёнными, остальные набираются выделением как обычно.

Депозит **безвозвратен**: предметы уходят из инвентаря, вернуть их через ResetInput нельзя
(в отличие от обычного выделения).

## Прогресс UI (вариант B)

Инлайн на ячейке требования `inputGrid`, без отдельной строки:

- **Бейдж** — `Label`, прижатый к нижней кромке ячейки, текст `"{внесено} / {нужно}"`. Заменяет
  ванильную подпись количества (`Details/Amount`) у ячейки, пока бейдж присутствует (числа не дублируем).
- **Закрытый слот** (внесено ≥ нужно) — бейдж превращается в `✓`, ячейка получает зелёное состояние
  `State("Selected")`.
- **Частичный слот** — бейдж `"{внесено} / {нужно}"`, опциональный уголок «осталось N».
- Задачи без `deliver` и слоты без прогресса — ванильный вид, бейдж не добавляем.
- Точная подпись/цвета — из макета `docs/mockups/partial-tasks/index.html` (вариант B), но ноды
  строим нативными (Label + StyleBoxFlat), без SVG-текстур.

## Точки интеграции (хуки)

Регистрируются в `VTKHooks._do_register()` рядом с существующими, имена — **строковыми литералами**
(wrap-surface фиксируется сканом литеральных `.hook("...")`; иначе метод не обернётся). Идентификаторы
хуков держим в отдельном массиве `_hooks_deposits` рядом с `_hooks_kc`.

- `interface-initializetasks-post` (void, `_lib._caller` = `Interface`) — построить кнопки Deposit и
  бейджи на всех карточках, навесить сигналы.
- `interface-startinput-post` — после смены режима ввода перерисовать бейджи и удовлетворённые ячейки
  (ваниль снимает выделения).
- `task-_on_complete_pressed` (replace) — `_lib._caller` = узел `Task`:
  - если леджер покрывает: выполнить завершение сами (см. ниже) и `skip_super()`;
  - иначе — не трогать, ваниль завершает как обычно.
- `trader-completetask-post` (уже зарегистрирован в 4.11.0) — дополнительно очистить леджер задачи.

Хук `task-cancomplete` **не** переопределяем. Дамп загрузчика (`rtvsrc/Scripts/Trader.gd`, `Item.gd`)
показывает: у методов, возвращающих значение, обёртка берёт результат замены только при `skip_super`,
а у void-метода `Task.CanComplete()` возврат замены **отбрасывается** — на исход влияет только
`skip_super`. `CanComplete()` не возвращает флаг, а выставляет `completeButton.disabled`; поэтому
`skip_super()` на покрытом пути отменил бы единственный эффект (кнопку Complete для покрытой задачи),
а `return true` ничего не значит. `CanComplete()` зовётся только из `AddInputItem`/`RemoveInputItem` и
один раз из обработчика Deposit. Поэтому рендер сам выставляет доступность: закрытые слоты помечаются
`State("Selected")`, а `_render_task_card` при полном покрытии снимает `disabled` с
`Margin/Elements/Buttons/Complete`. Частичную сдачу ведёт ваниль (её `CanComplete` видит живое выделение).

Завершение по леджеру без повторного списания:

```
card.Completed()                   # UI карточки «Delivered», кнопки гаснут (как ванильный _on_complete_pressed)
trader.CompleteTask(card.taskData) # + trader-completetask-post очищает леджер и заметку
iface.UpdateTraderInfo()
iface.inputTarget = card           # временно, чтобы GetOutputItems взял card.outputGrid
iface.isInputting = true
iface.GetOutputItems()             # выдать награды
# inputTarget/isInputting восстанавливаем
iface.ResetInput()
skip_super()
```

`DestroyInputItems` **не** зовём: предметы уже списаны депозитом, а живого выделения в инвентаре при
сдаче по леджеру нет. Смешанный случай (часть внесена, остаток выделен живыми стопками) идёт по
ванильному пути: леджер не покрыт → обработчик не трогает ваниль → `interface.Complete` списывает
выделенные стопки.

**Фантомные ячейки `inputGrid`.** Шаблон `Task.tscn` содержит 7 статичных детей в `Input_Grid`;
`Task.Initialize` освобождает их через `queue_free()` (отложенно) и добавляет реальные слоты. Хук
`interface-initializetasks-post` срабатывает в том же кадре, поэтому `inputGrid.get_children()` ещё
содержит 7 освобождаемых ячеек. Все обходы детей (сбор слотов, покраску, очистку бейджей, список
карточек `taskList`) ведём по «живым» детям — пропускающим `is_queued_for_deletion()`.

## Новый модуль `VTKDeposits.gd`

Префикс `VTK`, как остальные сущности. Чистая логика (headless, по образцу `Picker`/`Draft`/`Notes`) —
переносимая арифметика леджера над «нормализованными» словарями; доступ к узлам и ресурсам держит
`VTKHooks`. Ни `load()`, ни путей внутрь игры.

Чистая логика:

- `task_key(path: String, name: String, trader: String) -> String` — `path`, если непустой, иначе
  `name + "::" + trader`.
- `normalize_slots(entries: Array) -> Array` — из `[{ "file": String, "name": String, "amount": int }]`
  (живые слоты `inputGrid`) возвращает тот же порядок с целочисленными `amount` (≥1) и индексом.
- `coverage(ledger: Dictionary, key: String, slots: Array) -> Dictionary` — по каждому слоту
  `{ "index", "required", "deposited", "remaining", "satisfied" }` и `"all_satisfied": bool`.
- `apply(ledger: Dictionary, key: String, slots: Array, offered: Array) -> Dictionary` — распределяет
  `offered` (`[{ "file", "amount", "ref" }]` — выделенные стопки) по непокрытым слотам с тем же `file`
  (не больше остатка на слот, лишнее не трогаем); возвращает новую копию леджера и
  `"take": [{ "ref", "amount" }]` — сколько списать с каждой стопки.
- `clear_task(ledger: Dictionary, key: String) -> Dictionary` — копия без записи задачи.
- `badge_text(deposited: int, required: int) -> String` — `"{deposited} / {required}"`.
- `is_covered(coverage: Dictionary) -> bool` — `all_satisfied`.

Склейка (только рантайм, в `VTKHooks`):

- `_render_task_card(card)` — читает живые слоты `card.inputGrid`, зовёт `coverage`, рисует бейджи
  и удовлетворённые ячейки; при полном покрытии явно снимает `disabled` с кнопки Complete (ваниль
  пересчитывает его не в каждом пути) и перерисовывает доступность Deposit. Точный путь кнопки
  в `Task.tscn` ищем терпимо (по имени/тексту в `Buttons`), тела `Task.gd` скомпилированы.
- `_on_deposit_pressed(card)` — собирает выделенные стопки (`inventoryGrid` дети со `selected`),
  зовёт `apply`, списывает `take` из инвентаря, пишет леджер в метаданные `TraderSave`, сохраняет
  ресурс, перерисовывает карточку.
- `_ledger()` / `_save_ledger()` — чтение/запись мета `vtk_deposits` на `TraderSave` через
  `get_meta`/`set_meta` + `ResourceSaver.save`.

### Списание из стопки (проверено по ванильному `Interface.gd`/`Item.gd`)

Ванильный `DestroyInputItems` при сдаче задачи удаляет **целиком** выделенные узлы
(`inventoryGrid.Pick(child)` + `child.queue_free()`) — то есть списывает стопку полностью. Депозит
может брать **часть** стопки, поэтому для `amount < slotData.amount` делаем:

- `child.slotData.amount -= take`; `child.UpdateDetails()` (обновляет подпись количества);
- при `slotData.amount == 0` — `inventoryGrid.Pick(child)` + `child.queue_free()` (как ваниль);
- после обработки — `child.State("Static")` (снять выделение), чтобы сдача не списала остаток повторно.

Сопоставление по `slotData.itemData.file` (как в ванильном `AutoStack`), иначе по `name`.

## Края и устойчивость

- Задача без `deliver` — карточка без Deposit и без бейджей.
- Нет `user://Traders.tres` — леджер пустой; Deposit пишет метаданные, при необходимости создавая
  ресурс (как `Loader.SaveTrader`).
- `resource_path` пустой — ключ по `name::trader`; стабильность между открытиями вкладки сохраняется
  (тот же `TaskData`-инстанс кэшируется по пути у загрузчика).
- `CanComplete`/`_on_complete_pressed` не найдены (переименование в апдейте игры) — хук не срабатывает,
  механика молча деградирует до ванильной; проверить лог загрузчика после апдейта. Имена методов —
  из декомпиляции референса, не подтверждены рантаймом.
- Смешанная сдача (часть внесена, часть выделена предметами): закрытые слоты помечаются
  удовлетворёнными, остальные набираются выделением; replace `task-cancomplete` и явное включение
  Complete в `_render_task_card` страхуют гейт.
- Двойное списание исключено: Deposit списывает в момент нажатия (в т.ч. частично из стопки, с
  `State("Static")` после), а ванильный `DestroyInputItems` при финальной сдаче находит только то,
  что игрок выделил сам.
- Чужой мод на тот же replace-хук — загрузчик берёт первый (first-wins): наш replace может уступить
  чужому. `task-cancomplete` безопаснее переопределять через `skip_super`-ветку; конфликт — известный
  риск, фиксируем в заметке.
- Двойное списание исключено: Deposit удаляет предметы сразу, а ванильный `DestroyInputItems` при
  финальной сдаче ничего не находит (inventory-cleared).
- Ноды/поля достаём через `get_node_or_null`/`get(...)`; отсутствие узла или поля — тихий пропуск.
