# Freeze for JCM — дизайн 1.1.0 (Freeze BTR & Heli + Hotkey)

Дата: 2026-10-19
Статус: черновик на ревью
База: релиз 1.0.0 (`docs/superpowers/plans/2026-10-19-jcm-freeze.md`), спека `docs/superpowers/specs/2026-10-19-jcm-freeze-design.md`

## Что делаем в 1.1.0

Три вещи, все — приращения к уже работающему аддону:

1. **Freeze BTR & Heli** (`jcm-freeze.vehicles`) — третий и четвёртый replace-хуки: BTR и вертолёт-ивент замирают при включённом тумблере, включая свежий спавн.
2. **Подавление звука BTR** — при заморозке глушим двигатель, при выключении возвращаем (пользовательское решение).
3. **Хоткей Freeze NPC** — настраиваемая в MCM клавиша переключает тумблер Freeze NPC. Хоткей только для NPC (пользовательское решение); технике клавишу не заводим.

## Открытия по исходникам (проверено)

**Вертолёт `Helicopter.gd`** (деток `RTVcopy/extracted/Scripts/Helicopter.gdc`, 321 строка). Самое важное:

- `_physics_process(delta)` (93) — весь полёт: `RotorBlades`, `Flyby/Patrol/Attack`, `Sensor`, `Searchlight`. Пропуск — полная статика в воздухе.
- Вертолёт — обычный `Node3D` (1), **не** RigidBody; падать не будет, пока не вызовут `DistanceClear`/`queue_free`.
- НО: `DistanceClear()` (208) умирает в **том же** `_physics_process` (94), через `queue_free`. То есть при заморозке вертолёт застывает, **если он внутри 2000 м от центра**; если в момент включения он уже дальше — пропуск `_physics_process` его «консервирует» навсегда, пока тумблер включён. Это едва ли реальный сценарий (ивент-вертолёт работает у игрока), но отметим как известный риск, а не как фолбек.
- Аналогично `RocketHelicopter.gd` — это **снаряд** ракеты вертолёта (`Assets/Rocket/Rocket_Helicopter.tscn`), `_physics_process` ведёт полёт. По спеке снаряды **не замораживаем** — хук на него не ставим.

**BTR `BTR.gd`** (деток, 642 строки):

- `_physics_process(delta)` (146) зовёт `Audio(delta)` (154) → `Audio` (569) двигает громкости `idleAudio`/`driveAudio`/`roadAudio` через `move_toward` к целевым значениям.
- Аудиоплееры на автоплее: `_ready` (120) делает `idleAudio.play()`, `driveAudio.play()`, `roadAudio.play()` (137–139). Это `AudioStreamPlayer3D`, играют сами, скрипт их только микшует.
- Значит пропуска `_physics_process` мало: двигатель продолжит звучать на последней громкости. Для «замер, тишина» нужно явно обнулить/остановить.

**Спавн** (`AISpawner.gd`, деток, 491 строка): пул наполняется в `CreatePools` (132) через `newEnemy.Deactivate()` (148 и др.); спавн — `newEnemy.reparent(enemies)` + `Activate("Wander")` (254–260). Обычный `reparent` без `add_child(..., true)`, так что `process_mode` пуловых узлов не трогается — `Deactivate()` ставит `process_mode = DISABLED` на самом AI-узле (AI.gd:170), а `Activate()` возвращает `INHERIT` (AI.gd:213). Вывод: **флаг-хуки размораживают свежий спавн сами** (как и в 1.0.0 для NPC), отдельного ре-применения не нужно.

**Хоткей в JCM** (JCM `Main.gd`):

- Настройки идут через MCM: `_add_mcm_value(config, "Keycode", key, "Hotkeys", {...})` (167) + чтение `_mcm_value(config, "Keycode", key, fallback)` (180, 189–193).
- Слушатель `_input(event)` (440): только `InputEventKey`/`InputEventMouseButton`, только `event.pressed`; `_hotkey_pressed(event, action, fallback_keycode)` (483) — `InputMap.has_action(action) ? event.is_action_pressed(action) : physical_keycode == fallback`.
- MCM регистрирует каждый Keycode как InputMap-акцию (`MCM_Helpers.gd:219`), потому `is_action_pressed` и достаёт переназначенную клавишу. Это ровно тот же паттерн, что нам нужен.
- Гейт по UI: `if not gameData.menu and not gameData.settings and not get_viewport().gui_get_focus_owner() is LineEdit` (457).

**MCM как зависимость** (пользовательское решение):

- `mod.txt` MCM: `id="doinkoink-mcm"`, `priority=-100`, автолоад `mcm="res://ModConfigurationMenu/Main.gd"`. MCM грузится **до** JCM (`priority=-1`) и до нашего аддона.
- Регистрация с MCM-стороны: `MCM_Config.new(mod_id, name, desc, save_cb, self)` + цепочка `CreateKeycodeValue(...)` + `RegisterMod()` (MCM_Config.gd:82, 234). Наш аддон заводит **свою** MCM-секцию (`jcm-freeze`), как сделал бы любой мод, и читает свой `config.ini`.
- Файл настроек MCM на мод: `user://MCM/jcm-freeze/config.ini` (и `<profile>.ini`).

## Механизм заморозки техники

Пo образцу 1.0.0: хуки регистрируются один раз, в колбэке решает флаг.

```gdscript
func _on_btr_process(_delta) -> void:
	if _vehicles_on:
		_silence_btr()
		_lib.skip_super()

func _on_heli_process(_delta) -> void:
	if _vehicles_on:
		_lib.skip_super()
```

- `btr-_physics_process` и `helicopter-_physics_process` — replace-слоты (bare имя, без суффикса) + литеральные `.hook("...")` и `[hooks]`-декларации (контракт wrap-поверхности 14510–14514).
- Оба колбэка принимают ровно `_delta` (BTR.gd:146 — untyped 1 арг; Helicopter.gd:93 — untyped 1 арг).

### Звук BTR

На **первом** кадре заморозки глотаем узел BTR и запоминаем его:

```gdscript
var _bt_audio: Array = []          # записи: {node, saved} для restore
var _bt_seen: Dictionary = {}      # id узла -> bool (не дублировать)

func _silence_btr() -> void:
	var btr = _lib._caller
	if btr == null or not is_instance_valid(btr):
		return
	var key = btr.get_instance_id()
	if _bt_seen.has(key):
		return
	_bt_seen[key] = true
	for name in ["Idle", "Drive", "Road"]:
		var player = btr.get_node_or_null("Audio/" + name)
		if player == null:
			continue
		_bt_audio.append({"node": player, "volume_db": player.volume_db, "playing": player.playing})
		player.stop()
```

- Ключ — `get_instance_id()`; чистим записи о мёртвых узлах в `_off_pass` (прогон по `_bt_audio`, `is_instance_valid`).
- Восстановление: при выключении тумблера идём по `_bt_audio`, `play()`/`volume_db` возвращаем. Проще всего — на первом же кадре с `_vehicles_on == false` после заморозки.
- `_lib._caller` внутри wrapper'а = сам инстанс BTR (устанавливается `21326`), поэтому `_silence_btr` из колбэка видит нужный узел. Это тот же приём, что JCM в своём примере (`_lib._caller.gravityMultiplier`).
- **Восстановление** делает `_on_vehicles_toggled(false)`: идёт по `_bt_audio`, для живых узлов возвращает `volume_db` и `play()` там, где играло. Плюс `_on_btr_process` в кадре с `!_vehicles_on` чистит `_bt_seen`/`_bt_audio` от мёртвых (`is_instance_valid`). Флаг переключается из JCM-колбэка до следующего кадра, так что «выключили» и «вернули звук» идут одной транзакцией.

**Риск/открытый вопрос**: если у события одновременно несколько BTR, каждый найдётся своим колбэком. Если BTR убивают (`Death`) во время заморозки — узел освободится, запись почистится по `is_instance_valid`.

### Вертолёт

Фолбек с `process_mode = DISABLED` **не нужен**: вертолёт кинематический, пропуска `_physics_process` достаточно, чтобы он застыл в воздухе. Единственная тонкость — `DistanceClear` (умирает в том же методе): замороженный вертолёт не самоочистится, пока тумблер включён. Это ожидаемо (замер = стоп). Если после выключения вертолёт уже за 2000 м — умрёт в тот же кадр, как и задумано.

## Хоткей

### Регистрация (FreezeMCM.gd)

Тонкий слой над MCM:

```gdscript
extends Node

const MOD_ID = "jcm-freeze"
const KEY_ID = "freezeNpcKey"
const CONFIG_PATH = "user://MCM/jcm-freeze/config.ini"

var key_freeze_npc: Key = KEY_KP_4
var _mcm_config = null

func _ready() -> void:
	if not Engine.has_meta("RTVModLib"):
		return
	var lib = Engine.get_meta("RTVModLib")
	if lib.get("_is_ready"):
		_register()
	else:
		lib.frameworks_ready.connect(_register)

func _register() -> void:
	var lib = Engine.get_meta("RTVModLib")
	if not lib.has_mod("doinkoink-mcm"):
		return

	_mcm_config = MCM_Config.new(MOD_ID, "Freeze for JCM",
		"Freeze NPCs and vehicles on demand.", _on_mcm_saved, self)

	_mcm_config.CreateKeycodeValue(KEY_ID, "Toggle Freeze NPC",
		"Turns Freeze NPC on or off without opening the menu.",
		key_freeze_npc, MCM_Config.MCM_Key_Types.KEY) \
		.setCategory("Hotkeys")

	_mcm_config.RegisterMod()

func _on_mcm_saved(config: ConfigFile) -> void:
	key_freeze_npc = _mcm_value(config, "Keycode", KEY_ID, key_freeze_npc)

func _mcm_value(config: ConfigFile, section: String, key: String, fallback):
	if config.has_section_key(section, key):
		var entry = config.get_value(section, key)
		if entry is Dictionary and entry.has("value"):
			return entry["value"]
	return fallback
```

- `MCM_Config` — глобальный класс MCM (`class_name MCM_Config`), доступен как тип при загруженном MCM. Статический анализатор `.check` MCM не знает, поэтому `MCM_Config` в standalone-проверке будет Parse Error. **Решение**: стенд парсинга оборачивает MCM-скрипт в проект с **заглушкой** `MCM_Config` (см. «Проверка»).
- `RegisterMod()` MCM сам зовёт `FileOnSaveCallback` при регистрации и сохранении, поэтому отдельный ручной `_load_config()` не нужен: MCM отдаёт `config` в `_on_mcm_saved`, оттуда и берём `key_freeze_npc`. `CONFIG_PATH` держим только для справки/отладки — читать его вручную не нужно.
- Дефолт `KEY_KP_4` — свой, свободный: у JCM заняты KP_0 (меню), KP_1, KP_2, KP_3 (спавн).

### Слушатель (Main.gd)

```gdscript
func _input(event: InputEvent) -> void:
	if _jcm == null or _mcm == null:
		return
	if not (event is InputEventKey or event is InputEventMouseButton) or not event.pressed:
		return
	var keycode: int = _mcm.key_freeze_npc
	if not _hotkey_pressed(event, "freezeNpcKey", keycode):
		return
	if get_viewport().gui_get_focus_owner() is LineEdit:
		return
	var gd = _jcm.get("gameData")
	if gd == null or gd.menu or gd.settings:
		return
	_jcm.set_enabled(NPC_ID, not _jcm.is_enabled(NPC_ID))


func _hotkey_pressed(event: InputEvent, action: String, fallback_keycode: int) -> bool:
	if InputMap.has_action(action):
		return event.is_action_pressed(action)
	return event is InputEventKey and not event.echo and event.physical_keycode == fallback_keycode
```

**Доступ к `gameData.menu`/`gameData.settings`**: JCM грузит `res://Resources/GameData.tres` как ресурс и читает `.menu`/`.settings` (`Main.gd:457`). Наш аддон ресурсов не прелоадит (принцип «без `load()` в Main» — чтобы парсился без игровых стабов). Берём инстанс у JCM: `_jcm.get("gameData")`; JCM держит прелоад и отдаст свой объект. Гвард на `null`. Это снимает `load()` и совпадает с политикой «тянуть игровое состояние у уже поднятого соседа».

**Синхронизация двух источников правды**: тумблер в JCM пушит `on_toggled` → `_npc_on`; хоткей идёт через `set_enabled` → JCM сам зовёт `on_toggled` → тот же `_npc_on`. Флаг остаётся единственным состоянием, рассинхрона нет. UI вкладки AI обновится, даже если меню открыто (MCM/JCM документируют это).

## Гварды

- `hook()` на каждый из трёх replace-слотов: `-1` → `push_warning`, остальные живут.
- MCM-регистрация: `has_mod("doinkoink-mcm")`; нет MCM → хоткей не заводим, тумблеры работают.
- `_lib._caller` в `_silence_btr` — `null`-гвард, `is_instance_valid`.
- Хоткей: `_jcm`/`_mcm` null-гварды; фокус в `LineEdit` и меню/настройки — не срабатывает.
- `set_enabled` доступен с JCM 3.5.0 (проверено, `Main.gd:892`); мы и так гейтим `supports_addon_api("1.0")`.

## Известные риски

- **`DistanceClear` вертолёта**: замороженный вертолёт не самоочистится до выключения тумблера (ожидаемо). Если вертолёт вне 2000 м в момент включения — он и застынет вне зоны, потом умрёт после выключения.
- **BTR-звук и старт-сэмплы** (`startAudio`/`endAudio`) не глушим: они разовые (`play()` по флагу `driveStart`), при заморозке не повторятся. Глушим только три луп-плеера.
- **Класс `MCM_Config`** в `FreezeMCM.gd`: если MCM грузится позже (нарушен порядок), `MCM_Config` не резолвится на этапе парсинга чужого проекта без заглушки — отсюда заглушка на стенде; в игре MCM `priority=-100` гарантирует подъём раньше.
- **Хоткей vs JCM-хоткеи**: `_input` у обоих; клавиши по умолчанию разные (наша — `KEY_KP_4`, свободна), конфликтов нет; переназначение — на игроке.
