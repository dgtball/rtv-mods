# Трёхшаговый выбор предметов в редакторе сета — дизайн

Дата: 2026-10-05
Статус: утверждён пользователем на интерактивном макете
Макет: `docs/mockups/picker-a2-interactive.html` (эталон поведения)
Харнесс макета: `python .check/a2/run.py` — 53 проверки, все зелёные

## Задача

Редактор сета сейчас один плоский список: поле названия, чипы типов предметов,
сетка всех предметов, список экипировки, список снаряжения, кнопки. Пользователю
приходится держать в голове, что есть сетка, что куда попадёт и что уже занято.
Дублирующийся фильтр по типу (`_type_index`, `_populate_item_grid`) конкурирует
с фильтром по слоту и вводит в заблуждение: карточка показывает «Primary», но
куда предмет встанет, видно только после клика.

Цель: заменить плоский редактор тремя свободно переключаемыми шагами
(Экипировка → Снаряжение → Готово), где всегда видно, что занято, куда попадёт
следующий клик и что получится на выходе.

## Принятые решения

1. **Три шага, навигация свободная.** Шаги — кликабельные вкладки, не мастер с
   принудительным `Next`. Возврат назад не должен быть болью.
2. **Слот — это цель, а не подпись.** Клик по строке слота задаёт destination и
   фильтрует сетку. Чип «Все предметы» сбрасывает destination, и размещение
   идёт авто: первый свободный слот из `slots` предмета, иначе снаряжение.
3. **Занятый слот вытесняется.** Клик по предмету в занятый слот заменяет
   содержимое. Вытесненный предмет уходит из сета целиком, а не в снаряжение:
   оружие или бронежилет в снаряжении бессмысленны, молча прятать предмет в
   другой слот опаснее, чем сделать его удаление явным (пользователь видит
   список и может добавить обратно одним кликом).
4. **Обвесы одиночные по группе.** Группа = `subtype` самого обвеса
   (`Sight`, `Muzzle`, `Grip`, …). Клик по другому обвесу той же группы
   заменяет текущий; повторный клик по выбранному снимает его. Два прицела на
   одном стволе — невалидное состояние, игнорируем.
5. **Панель не открывается, если открывать нечего.** Обвесы — когда есть
   `compatible`, тумблер заполнения — когда предмет сам обойма. Нет ни того, ни
   другого — панели нет. Надписи «Обвесов нет» не существует.
6. **Никакого справочного спама.** В шапке только метка текущего слота и чип
   «Все предметы». Счётчики «N подходит», пояснения про автоназначение и
   подписи назначения убираются.
7. **Название переезжает в шаг 3.** В шапке его больше нет. Поле остаётся тем же
   узлом `_name_input`, просто родителем становится третья страница, так что
   `_save_loadout()` читает его без изменений.
8. **Категория вместо чипов типов.** Полосы-разделители (`Оружие`, `Броня`,
   `Снаряжение`, `Гранаты`, `Патроны`, `Медицина`, `Еда`, `Инструменты`) внутри
   сетки заменяют фильтр по типу: он дублировал то, что видно по карточкам.
9. **Поиск — настоящий `LineEdit`.** В макете это заглушка.

## Архитектура

Три страницы строятся один раз в `_build_editor()`, переключение — это `visible`.
Никакой пересборки узлов при смене шага, иначе теряется фокус `_name_input` и
позиция скролла.

```
_build_editor()                     VTKUI.gd:408
├── _build_stepper()                новая: три кнопки-шага + статусные галочки
├── page0 = _build_page_equipment()
│     ├── _build_slot_list()        новая: строки слотов из данных
│     ├── LineEdit (поиск)
│     ├── ScrollContainer → GridContainer (#6 колонок, как сейчас)
│     └── панель обвесов владельца   переиспользует _build_attachment_panel
├── page1 = _build_page_gear()
│     ├── чипы снаряжения            −/+ счётчик, клик чика тогглит панель
│     ├── «+ Добавить» → сетка предметов
│     └── панель обвесов/обоймы
└── page2 = _build_page_done()
      ├── сводка сета
      ├── _name_input               переехал сюда
      └── Save / Clear / Cancel
```

Состояние остаётся в `_draft` (`VTKDraft`), в UI добавляется только
`_target_slot: String` и переиспользуется существующий `_open_att_path: String`
как идентификатор единственной открытой панели. Две открытые панели в макете не
предусмотрены, поэтому одного `_open_att_path` достаточно.

### Новые функции в `VTKUI.gd`

| Функция | Ответственность |
|---|---|
| `_all_slots() -> Array` | Список слотов для шага 1 |
| `_build_slot_list()` | Строки слотов с фильтрацией цели |
| `_set_target_slot(slot: String)` | Переключение destination, пересборка сетки |
| `_items_for_target() -> Array` | Фильтр по слоту + поиск |
| `_place_item(item, type_name)` | Маршрутизация: в цель, авто, или gear |
| `_build_stepper()`, `_show_page(n)` | Навигация по шагам |
| `_refresh_slot_list()` | Перерисовка строк слотов (бывшая часть `_refresh_draft_ui`) |
| `_refresh_gear_chips()` | Перерисовка чипов снаряжения (бывшая часть `_refresh_draft_ui`) |
| `_build_page_done()` | Сводка + имя + действия |
| `_refresh_summary()` | Пересборка сводки |
| `_notify_draft_problem(msg)` | Ошибки сохранения с переходом на нужный шаг |

`_refresh_draft_ui()` в текущем виде рисует и экипировку, и снаряжение
(`VTKUI.gd:632–727`). В трёхшаговой раскладке они живут на разных страницах, поэтому
функция разбивается на `_refresh_slot_list()`, `_refresh_gear_chips()` и
`_refresh_summary()`. Общий публичный вход не нужен: каждая страница обновляет
себя, а изменение черновика вызывает все три.

Редактор пересобирается только из `_start_new_draft()`, `_edit_loadout()` и
`_cancel_draft()`. `_switch_tab()` (`VTKUI.gd:358–374`) лишь скрывает и показывает
контейнер вкладки, а `_refresh_all()` не трогает `_editor_panel`, поэтому страницы,
`_name_input` и позиция скролла переживают переключение вкладок. `_target_slot` и
`_search_text` сбрасываются в трёх точках пересборки; при редактировании
существующего сета `_target_slot` не восстанавливается — он относится к навигации
по текущей сессии, а не к сохранённым данным.

### Новые функции в `VTKDraft.gd`

Черновик остаётся чистой логикой: он не вызывает `load()` и не знает про игру,
иначе его нельзя тестировать headless. Всё, что требует ресурсов, приходит
снаружи — строкой или `Callable`.

```gdscript
# Положить предмет в конкретный слот. Занятый слот вытесняется.
# "" означает «слот непригоден» — вызывающий код откатывается на add().
func add_to_slot(path: String, item_name: String, slots, amount: float,
        type_name: String, slot: String, counted: bool = false) -> String

# Обвес одиночный по группе. grp_of — Callable: путь обвеса -> группа.
# Он же используется, чтобы выбросить прочие обвесы той же группы.
func toggle_attachment(owner_path: String, att_path: String,
        grp: String, grp_of: Callable) -> void
```

`grp_of` в UI — лямбда, которая грузит ресурс и достаёт `subtype`. В тестах
подставляется заглушка, поэтому `VTKDraft` не тянет `load()`.

## Переименование файла сетов

`loadouts.json` → `VTKsets.json`, в `user://MCM/vostok-toolkit/`. Имя
`loadouts/` у папки мода и `Loadouts.vmz` у пакета остаётся: переименовывается
только пользовательский файл, чтобы он назывался так же, как остальные сущности
мода (`VTK*`, `vostok-toolkit`).

Простое переименование обнулило бы сеты: мод открылся бы с «Нет сохранённых
сетов», и причина была бы неочевидной. Поэтому перенос одноразовый и по образцу
`_migrate_mcm_dir()` (`VTKUI.gd:95`), который уже переносит папку
`MCM/loadouts` → `MCM/vostok-toolkit`.

В `VTKData.gd`:

```gdscript
const SAVE_FILE := "user://MCM/vostok-toolkit/VTKsets.json"
const LEGACY_SAVE_FILE := "user://MCM/vostok-toolkit/loadouts.json"

# Одноразовый перенос loadouts.json -> VTKsets.json.
static func migrate_save_file() -> void
```

Правила, повторяющие `_migrate_mcm_dir()`:

- если `VTKsets.json` уже есть — выход, ничего не трогаем;
- если `loadouts.json` нет — выход;
- копируем содержимое, а не переименовываем: если удаление старого файла не
  удалось, данные всё равно уже на месте;
- каждая ошибка пишется в лог `[VTK] save file migration failed: ...`;
- старый файл удаляется только после успешной записи нового.

Рядом с `loadouts.json` у пользователей лежит `loadouts.json.bak` — текущий код
его не пишет и не читает, это остаток старой версии, но данные там есть, поэтому
перенос уводит и его: `VTKsets.json.bak`. Логика та же, флагов на два набора
файлов не нужно — цикл по паре «имя, имя.bak».

Вызов — из `_init_later()` (`VTKUI.gd:136`) рядом с `_migrate_mcm_dir()`, чтобы обе
одноразовые миграции были в одном месте при старте. `get_all()` остаётся чистым
читателем и ничего не создаёт на лету.

Формат записи не меняется, миграция переносит байты как есть. `4.4.0` ещё не
вышел, поэтому нового файла ни у кого нет и трёх сценариев не нужно: только
`loadouts.json` от `4.3.3` и старше.

Попутно правится отладочная подпись пути в `VTKUI.gd:521` — она печатает старый
путь и после переименования соврёт.

## Модель данных

Формат сохранения **не меняется**. `attachments` остаётся плоским массивом путей,
ровно как его читает `VTKData._build_slot_data()` (`VTKData.gd:475–486`). Одиночность
обеспечивается на записи, а не форматом, поэтому `loadouts.json` остаётся
совместимым и старые сеты продолжают применяться. По регламенту это фича, а не
несовместимое изменение: версия `4.3.3 → 4.4.0`.

Инварианты, которые поддерживает код:

- Один предмет — один слот из его `slots`. `add()` уже это гарантирует через
  `free_slot_of()`.
- Не более одного обвеса на группу у одного владельца.
- Обойма (`Attachment` + `subtype == "Magazine"`) не имеет обвесов: её
  `amount` целиком задаёт `full_mag`, вложенные патроны игра не читает
  (`VTKData.gd:476–480`). Отсюда же панель обоймы — это тумблер, а не список.

### Совместимость со старыми сетами

Ничего не мигрируется и формат не меняется. Прежняя панель показывала все прицелы
и выбирался один — то есть в сете оказывался один. Формально `CheckButton`
позволял отметить несколько, но на практике этого не делали, а тестовые сеты всё
равно пересоздаются, поэтому держать миграцию ради этого незачем.

Если всё же откроется сет, где в одной группе два обвеса, панель покажет оба
отмеченными — честно, по факту наличия в `attachments` — и первым же кликом
схлопнется к одному: `toggle_attachment()` выбросит прочих из группы. Расхождение
чинится лениво, без потери данных и без отдельного кода.

## Поведение по шагам

### Шаг 1 — Экипировка

Список слотов сверху, сетка снизу, в шапке — метка текущего слота и чип
«Все предметы».

- Клик по строке слота: строка подсвечивается, сетка фильтруется по `slots`
  предмета, шапка показывает имя слота.
- Клик по карточке: предмет кладётся в текущий слот через `add_to_slot()`;
  если слот занят — вытесняет содержимое. Затем открывается панель обвесов, если
  предмету есть что показать.
- Клик по строке уже занятого слота, когда он же является целью: панель обвесов
  открывается или закрывается. Снятие предмета — отдельная кнопка `✕` на строке.
- Чип «Все предметы»: destination сброшен, сетка полная, клик по карточке идёт
  через `add()` — первый свободный слот, иначе снаряжение.
- Карточка помечена золотой рамкой, если предмет уже в сете; у снаряжения
  дополнительно показывается `×N`.
- Поиск сужает выборку внутри текущего слота, а не заменяет его: слот `Head` плюс
  «апт» даёт аптечки, годные в голову. Строка сравнивается без учёта регистра по
  всему названию предмета. Очистка поля возвращает полный список для слота, чип
  «Все предметы» — полный список без фильтра. Поиск живёт в `_search_text` и
  переживает переключение вкладок.

Слоты берутся из данных: объединение `slots` всех предметов в `_db_items`.
Порядок вывода — предпочтительный (`Primary`, `Secondary`, `Melee`, `Body`,
`Head`, `Backpack`, `Pouches`, `Grenade_1`, `Grenade_2`, `Flashlight`, `Radio`),
причём предпочтительные, которых нет в данных, не показываются, а найденные вне
списка добавляются в конец. Так обновление игры не рисует пустых слотов, а новый
слот не теряется.

### Шаг 2 — Снаряжение

- Чипы: имя, `−`, количество, `+`, `✕`. Клик по чику тогглит панель, `✕` удаляет.
- `+ Добавить` открывает сетку предметов для снаряжения. Клик по карточке кладёт
  предмет в снаряжение и закрывает сетку; обвесы открываются только если они есть.
- Обойма: клик открывает панель с тумблером «Полная обойма — N патронов».
  Выключено = 0. Это переиспользует существующий `_build_magazine_panel()`
  (`VTKUI.gd:926`), меняется только вид, не логика.
- Уменьшение количества до нуля удаляет предмет и его обвесы — это уже так в
  `set_gear_amount()` (`VTKDraft.gd:138`).

### Шаг 3 — Готово

Сводка: занятые слоты с названиями, снаряжение с количествами, обвесы по группам,
состояние обойм. Ниже `_name_input` и кнопки.

`_save_loadout()` (`VTKUI.gd:1307`) сейчас молча выходит на трёх проверках. Новое
поведение:

| Условие | Действие |
|---|---|
| Название пустое | Фокус в поле, подсказка «Нужно название» (кнопка уже на шаге 3, переходить некуда) |
| Сет пуст | Переход на шаг 1, подсказка «Сет пуст» |
| Название занято | Как сейчас: поле очищается, placeholder «Название уже занято» |
| Ок | Сохранить, обновить список, остаться на шаге 3 |

«Очистить» и «Отмена» уже разведены в production: `_clear_draft()` чистит
содержимое, `_cancel_draft()` выбрасывает черновик целиком. В макете они
совпадали, в коде — нет, и код правый.

## Краевые случаи

| Случай | Поведение |
|---|---|
| У предмета нет `slots` или поле не массив | `_item_slots()` возвращает `[]`, предмет уходит в снаряжение. Уже так |
| Клик по карточке с destination, к которому предмет не подходит | Слот отбрасывается, размещение идёт авто |
| Сетка пуста после фильтра | Текст «Ничего не подходит», без пустых карточек |
| Ресурс предмета не грузится | Карточка строится без иконки, слоты пустые, предмет в снаряжение |
| Обойма без обвесов | Панель только с тумблером, группы не рисуются |
| У предмета `compatible` пуст | Панели нет вовсе, метки `◆` нет |
| Снят последний обвес оружия | `VTKData.gd:487–493` добавит в `nested` обойму из `compatible` — это поведение игры, не наша ошибка |
| Два предмета в один слот | Невозможно: `add_to_slot()` вытесняет, `add()` берёт свободный |

## Тестирование

1. `powershell -NoProfile -ExecutionPolicy Bypass -File .check\check.ps1` — парсинг
   и компиляция всех семи скриптов.
2. `python .check\encoding_check.py` — UTF-8 без BOM, переводы, версия в паке.
3. `python .check\keycheck.py` — каждый вызов `Loc.txt("...")` имеет запись в `RU`.
   Скрипт был указан в `AGENTS.md`, но в репозитории отсутствовал; восстановлен, на
   текущем коде даёт 67 ключей без рассинхрона. Смысл проверки в том, что
   отсутствие перевода не ломает вёрстку, а молча оставляет английский текст.
4. `python .check\a2\run.py` — регрессия поведения макета, на который опирается
   дизайн. Спека считается выполненной, только если макет и код не разошлись.
5. `.check/project/tests/test_draft.gd` — новые кейсы:
   - `add_to_slot` в свободный слот, в занятый (вытеснение), в непригодный
     слот (откат на `add()`), кратные слоты `Grenade_1`/`Grenade_2` по очереди;
   - `toggle_attachment`: замена внутри группы, снятие повторным кликом, другие
     группы не затрагиваются;
   - обоймы: `shown_count`, `is_full`, `set_full_mag` не сломаны;
   - `to_saved()`/`load_from()` round-trip не теряет `attachments` и `count`.
6. Ручная проверка в игре: три шага переключаются без пересборки, фокус имени
   переживает переключение, сохранение и повторное применение сета даёт то же, что
   показывает сводка.
7. Ручная проверка миграции файла: положить `loadouts.json` с парой сетов и
   `loadouts.json.bak` в `user://MCM/vostok-toolkit/`, запустить игру, убедиться,
   что сеты на месте, файлы переименованы, а в логе есть строка о переносе.
   Второй запуск не должен ничего менять.

## Локализация

Новые строки в UI требуют записи в `RU` того же прохода (`VTKLoc.gd`):
`Done`, `All items`, `Search items...`, `Loadout name`, `Set is empty`,
`Loadout name required`, `Nothing fits`, `Full magazine` (уже есть), `Empty`
(уже есть). Названия предметов, типов, слотов, трейдеров и убежищ не
локализуются — они приходят из `Database`, и перевод сломал бы поиск.

## Вне объёма

- Полноценные иконки по типам вместо иконки из ресурса.
- Перетаскивание мышью.
- Сортировка сетки.
